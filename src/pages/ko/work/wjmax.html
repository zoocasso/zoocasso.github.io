홈/시스템/WJMax 게임 서버

커뮤니티 리듬게임의 서버,
업데이트 때 최대 {{f:wjmax_peak}} 동시 접속

두 사람이 만든 커뮤니티 리듬게임 WJMax에서 서버·DB·보안을 맡았습니다. 게임 클라이언트는 다른 한 명이 만들었습니다. 공개한 서버 코드에서는 부하와 재전송, 입력 검사 문제를 테스트로 다룹니다.

아키텍처

게임 클라이언트는 곡마다 차트 8개의 플레이 횟수를 보고로 보내고, 서버는 이를 받아 데이터베이스에 저장했습니다.

직접 구축 다른 주체
{{inc:flow-wjmax}}
결과업데이트 날 최대 {{f:wjmax_peak}} 동시 접속을 받아 운영서버 로그 같은 원자료는 남아 있지 않아, 운영이 끝난 뒤 처음 정리한 기록(2025년 포트폴리오)의 값을 씁니다

공개 정리본에서 다룬 문제

게임 클라이언트가 보내는 요청은 그대로 두고, 서버 쪽 문제를 하나씩 테스트로 고정했습니다.

  1. 동시 접속이 몰릴 때 요청이 실패하던 문제

    문제
    정리 초기 버전은 요청이 데이터베이스 연결을 너무 일찍 잡는 구조라, 60명이 동시에 보내는 시험에서 요청의 절반 가까이가 서로 기다리다 실패했습니다.
    해결
    연결을 잡아 쓰고 돌려주는 일을 작업 스레드 하나 안에서 끝내게 하고, 연결 수를 작업 스레드 수(40)와 맞췄습니다. 60명 동시 시험을 CI에 넣어 모두 응답이 오는지 계속 확인합니다.

  2. 재전송된 보고의 중복 저장

    문제
    연결이 끊겨 같은 보고가 다시 오면 플레이 횟수가 두 번 쌓일 수 있습니다.
    해결
    클라이언트가 보고 ID를 보내면 같은 ID는 한 번만 저장합니다. 두 번이 동시에 와도 키 제약으로 두 번째가 첫 번째를 기다리고, 같은 ID에 다른 내용이 오면 409로 거절합니다. 다만 배포된 클라이언트는 ID를 보내지 않아, 그 재전송은 서버가 ID를 붙여 별개의 보고로 저장합니다.

  3. 곡 제목이 서로 합쳐지는 문제

    문제
    MySQL 기본 콜레이션은 대소문자·가나 차이를 무시해 "Glory"와 "GLORY", "ゆめ"와 "ユメ"를 같은 곡으로 봅니다.
    해결
    제목과 ID를 바이트 그대로 비교하는 콜레이션(utf8mb4_0900_bin)을 쓰고, CI에서 이를 확인합니다.

  4. 인증 없는 클라이언트의 입력

    문제
    배포된 게임 클라이언트는 인증 정보를 보내지 않아, 주소를 알면 누구나 보고를 보낼 수 있습니다.
    해결
    입력을 파싱 전에 검사해 잘못된 입력은 422, 1 MB가 넘는 본문은 413으로 거절하고, 앞단의 Cloudflare와 함께 남용을 막습니다. 보고가 실제 플레이를 증명하지는 않는다는 한계도 README에 적었습니다.

테스트는 GitHub Actions에서 SQLite와 MySQL 8.0·8.4로 돌리고, schema.sql이 코드와 맞는지(타입, 콜레이션, 키, 인덱스)도 확인합니다.
