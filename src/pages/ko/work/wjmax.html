홈/시스템/WJMax 게임 서버

커뮤니티 리듬게임의 서버,
업데이트 때 접속이 몰리는 실사용 서비스

두 사람이 만든 커뮤니티 리듬게임 WJMax에서 서버·DB·보안을 맡았습니다. 게임 클라이언트는 다른 한 명이 만들었습니다. 공개한 서버 코드에서는 부하와 재전송, 입력 검사 문제를 테스트로 다룹니다.

게임 클라이언트는 곡의 차트별 플레이 횟수를 보고로 보내고, 서버는 이를 받아 데이터베이스에 저장했습니다.

공개 정리본에서 다룬 문제

게임 클라이언트가 보내는 요청은 그대로 두고, 서버 쪽 문제를 하나씩 테스트로 고정했습니다.

  1. 동시 접속이 몰릴 때 요청이 실패하던 문제

    문제
    정리 초기 버전은 요청이 데이터베이스 연결을 너무 일찍 잡는 구조라, 여러 요청을 동시에 보내는 시험에서 상당수가 서로 기다리다 실패했습니다.
    해결
    연결을 잡아 쓰고 돌려주는 일을 작업 스레드 하나 안에서 끝내게 하고, 연결 수를 작업 스레드 수와 맞췄습니다. 동시 요청 시험을 CI에 넣어 모두 응답이 오는지 계속 확인합니다.

  2. 재전송된 보고가 두 번 저장되는 문제

    문제
    연결이 끊겨 같은 보고가 다시 오면 플레이 횟수가 두 번 쌓일 수 있습니다.
    해결
    보고에 번호(보고 ID)가 붙어 오면 같은 번호는 한 번만 저장합니다. 같은 보고 두 개가 동시에 도착해도 하나만 저장되고, 번호는 같은데 내용이 다르면 거절합니다. 다만 지금 배포된 게임은 이 번호를 보내지 않아, 그 재전송은 여전히 별개의 보고로 저장됩니다.

  3. 곡 제목이 서로 합쳐지는 문제

    문제
    MySQL은 기본 설정에서 대문자와 소문자, 히라가나와 가타카나를 구분하지 않아 "Glory"와 "GLORY", "ゆめ"와 "ユメ"를 같은 곡으로 봅니다.
    해결
    제목과 ID는 글자 하나하나를 그대로 비교하도록 설정을 바꾸고, CI에서 이를 확인합니다.

  4. 누구나 보낼 수 있는 입력

    문제
    배포된 게임은 로그인 같은 인증 없이 보고를 보내서, 서버 주소만 알면 누구나 보고를 보낼 수 있습니다.
    해결
    서버가 내용을 읽기 전에 형식부터 검사해, 잘못된 입력과 지나치게 큰 요청은 바로 거절합니다. 앞단의 Cloudflare도 함께 남용을 막습니다. 보고가 실제로 플레이했다는 증명은 아니라는 한계도 README에 적었습니다.

테스트는 GitHub Actions에서 SQLite와 MySQL 8.0·8.4로 돌리고, 데이터베이스 정의 파일(schema.sql)이 코드와 맞는지도 확인합니다.
