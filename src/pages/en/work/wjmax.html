Problems handled in the public version

The request the game client sends stays as it was; the server-side problems were pinned down one by one with tests.

  1. Requests failing when many players send at once

    Problem
    The first draft of the public code took its database connection too early, so in a test with many clients sending at once, many of the requests ended up waiting on each other and failed.
    Fix
    The connection is now taken, used and returned inside one worker thread, and there are as many connections as worker threads. CI runs the concurrent-request test and checks that every request is answered.

  2. Retried reports stored twice

    Problem
    When a connection drops and the same report arrives again, its play counts can be added twice.
    Fix
    A report that carries a number (a report id) is stored only once per number. Two copies arriving at the same moment are still stored once, and the same number with different contents is refused. The released game sends no number, though, so its retries are still stored as separate reports.

  3. Song titles merging

    Problem
    By default MySQL does not tell upper from lower case or hiragana from katakana, so it treats “Glory” and “GLORY”, or “ゆめ” and “ユメ”, as the same song.
    Fix
    Titles and ids are compared exactly as written, character for character, and CI checks it.

  4. Input anyone can send

    Problem
    The released game sends its reports without any login, so anyone who knows the server's address can send one.
    Fix
    The server checks the format before it reads the contents and turns away malformed input and oversized requests right away; Cloudflare in front also helps hold off abuse. The README also states the limit: a report does not prove that a play actually happened.

GitHub Actions runs the tests on SQLite and on MySQL 8.0 and 8.4, and checks that the database definition (schema.sql) matches the code.
