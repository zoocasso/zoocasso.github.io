The game client reports the play count of each of a song's eight charts, and the server stores them in the database. A Cloudflare proxy and WAF sat in front of the server. The server was FastAPI packaged with Docker on EC2, and the database was RDS MySQL.

2026 rewrite

I cleaned up and rewrote the code from the live service in October 2026 (GitHub). The request the game client sends is unchanged; these are the problems the rewrite deals with.

  1. Connection pool starved under load

    Problem
    An early version of the rewrite took the database connection in a FastAPI dependency. In a local load test with 60 clients sending at once, 281 of 600 requests failed with a pool timeout.
    Fix
    The connection is taken inside the worker thread that runs the request, after its input has been checked, and the pool is sized to the 40 worker threads. CI runs the same test and checks that every client is answered.

  2. Retried reports stored twice

    Problem
    When a connection drops and the same report arrives again, its play counts can be added twice.
    Fix
    A report sent with an id is stored once per id. When two copies arrive at once, the key makes the second wait for the first, and the same id with different contents is refused with 409. The released client sends no id, though, so the server assigns one and its retries are stored as separate reports.

  3. Song titles merging

    Problem
    MySQL's default collation ignores case and kana, so it treats "Glory" and "GLORY", or "ゆめ" and "ユメ", as the same song.
    Fix
    Titles and ids compare byte for byte (utf8mb4_0900_bin), and CI checks it.

  4. Input from a client without authentication

    Problem
    The released game client sends no credentials, so anyone who knows the URL can post a report.
    Fix
    Input is checked before it is parsed: malformed input is a 422 and a body over 1 MB a 413, and Cloudflare in front bounds abuse. The README also states the limit: a report is not proof of who played.

GitHub Actions runs the tests on SQLite and on MySQL 8.0 and 8.4, and checks that schema.sql matches the code (types, collations, keys, indexes).
