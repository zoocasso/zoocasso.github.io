My part ran from the collection setup for shopping and procurement data to turning analysis models into FastAPI services and admin screens.

Key decisions

Why the collection method changed, and the rule used to clean the data.

  1. From crawling shopping sites to collecting through APIs

    Problem
    From 2022 to early 2023 the shopping sites were crawled directly. Even with the crawlers spread over {{f:kisti_farm}} (November 2022 to January 2023), collection kept getting blocked and interrupted, and direct crawling carried legal risk.
    Proposal
    I proposed collecting through official APIs instead, and in June 2023 this was agreed with the client, KISTI, and adopted. API data came in a clean format, which also made collection easy to automate.
    How
    Procurement data had come from the public data portal API since April 2023. Amazon moved to the Rainforest API (selected in July 2023, built from February to May 2024).

  2. De-duplication by product ID (ASIN)

    Problem
    The same product appeared in several categories at once, so collecting category by category produced overlaps.
    Result
    {{f:kisti_asin}} Amazon products became {{f:kisti_asin_dedup}}.

Scope

Not the whole project: the parts that were mine, listed separately.

What I built and ran

  • Selenium crawlers for Amazon and Danawa, a collector for the Public Procurement Service API on the public data portal, and crawling of the national procurement site
  • A distributed crawling farm on {{f:kisti_farm}} feeding one remote database, with de-duplication
  • Loading into central MySQL, {{f:kisti_rows}} in total as of November 2023
  • Batches for models 3, 4 and 5: project–company matching in SQL ({{f:kisti_match}}), price-band K-means (Dunn index), a daily KeyBERT review-keyword batch. In 2024, procurement statistics in SQL for model 3.1
  • FastAPI services and Jinja2 and Tabulator admin screens (filters, sequential runs, unified search, Excel export)
  • Moving Amazon collection to the Rainforest API (February to May 2024)
  • Moving the partner's prototype (models 1–2, a Java/Tomcat web app) to company servers and setting up its Docker runtime
  • Audit deliverables (operator manual, initial data-build report), presenting results in technical meetings, and handling data and code requests

What others did

  • KISTI researchers · commissioning and designing the project
  • University research teams (Sungkyunkwan University, Kookmin University) · algorithm design for some of the platform's models
  • A partner company · the prototype for models 1–2 and its Java/Tomcat web app
  • Another colleague · meeting minutes and reporting
